# Verification Engine 2.0

Verification is property-specific. Four evidence families coexist:

1. Numerical validation: independently recomputed continuity, energy, PDD service, boundary and operating constraints with explicit floating-point tolerances.
2. Empirical robustness: finite declared and held-out scenario outputs, unknown solver states, failures and conditional Wilson intervals.
3. Mathematical guarantees: precise propositions with explicit assumptions; no full hydraulic nonlinear guarantee is currently claimed.
4. Formal verification: bounded Boolean pipe-outage reachability checked with Z3, with SMT-LIB, proof object or counterexample, solver version, exact topology and assumptions.

A proof object contains requirement ID, proposition, model version, inputs, assumptions, tool, result, status, scope, limitations and evidence text/hash. A design that has a formally verified connectivity property is still only stress tested for its hydraulic service. The UI places the formal label next to that topology proposition, never next to the entire design or hydraulic solver.

The topology property is true under any single-pipe outage in the explicit passive undirected graph with all sources active. The two-outage query has a counterexample. Neither result establishes pressure, capacity, source availability, actual construction or field safety. The proof is generated by Z3 and is not independently checked by a separate proof kernel.

Evidence hashes protect canonical scientific payloads and exclude execution timestamps. Claim-ledger entries identify outputs supporting statements, assumptions, uncertainty/status, limitations and CLI/SMT reproduction routes. Rejected designs, solver failures and adversarial probes are retained. Formal unknown/timeouts never become success.
